1. PAGINAÇÃO COMPARTILHADA (DRY)
----------------------------------------------------------------------
Antes:
  Tanto EquipmentsService.findAll() quanto AdminService.findAllUsers()
  construíam o mesmo objeto de meta de paginação manualmente:
    {
      totalPages: Math.ceil(total / limit),
      hasNextPage: page * limit < total,
      hasPreviousPage: page > 1,
      ...
    }

Depois:
  Criado src/common/utils/pagination.ts com a função:
    buildPaginationMeta(total, page, limit): PaginationMeta
  Ambos os serviços agora chamam buildPaginationMeta().

Princípios:
  • DRY (Don't Repeat Yourself) — elimina duplicação
  • Single Responsibility — a responsabilidade de calcular metadados
    de paginação fica em um único lugar
  • Nome intencional — buildPaginationMeta comunica exatamente o que faz

Arquivos:
  src/common/utils/pagination.ts          (CRIADO)
  src/equipments/equipments.service.ts    (MODIFICADO)
  src/admin/admin.service.ts              (MODIFICADO)

2. REMOÇÃO DE CÓDIGO DUPLICADO EM findAll
----------------------------------------------------------------------
Antes:
  EquipmentsService.findAll() construía o filtro where inline, com a
  mesma lógica de buildWhereFromQuery() usada pelos métodos de export.

Depois:
  findAll() agora chama buildWhereFromQuery() — a mesma função privada
  já usada por exportCsv() e exportXlsx().

Princípios:
  • DRY — a lógica de montagem do filtro de busca existe uma vez
  • Single Responsibility — buildWhereFromQuery é a única fonte de
    verdade para construir o filtro

Arquivos:
  src/equipments/equipments.service.ts (MODIFICADO)

----------------------------------------------------------------------
3. NORMALIZAÇÃO COMPARTILHADA CSV/XLSX (DRY)
----------------------------------------------------------------------
Antes:
  Os métodos parseCsv() e parseXlsx() eram quase idênticos —
  ambos liam a planilha com XLSX.read(), obtinham a primeira aba
  e depois normalizavam as chaves/valores com trim(). A normalização
  estava duplicada em ambos.

Depois:
  • Criado um único método parseWorkbook() que recebe o parâmetro
    raw (true para CSV, false para XLSX).
  • Extraído o método normalizeRow() que centraliza o trim() de
    chaves e valores.
  • parseFile() chama parseWorkbook() + normalizeRow().

Princípios:
  • DRY — normalização existe em um único lugar
  • Abstração consistente — parseWorkbook esconde a diferença entre
    CSV e XLSX atrás de um parâmetro
  • Nível único de abstração — parseFile coordena, parseWorkbook lê,
    normalizeRow limpa

Arquivos:
  src/equipments/equipments.service.ts (MODIFICADO)

4. MENSAGENS PADRONIZADAS EM PORTUGUÊS
----------------------------------------------------------------------
Antes:
  • "No records found" (inglês) em findAll e findAllUsers
  • "Internal server error", "Record not found" no PrismaExceptionFilter
  • "Logged out successfully" no auth.controller

Depois:
  • "Nenhum equipamento encontrado" em findAll
  • "Nenhum registro encontrado" em findAllUsers
  • Mensagens do PrismaExceptionFilter em português:
    - "Registro não encontrado" (P2025)
    - "Já existe um registro com esse {campo}" (P2002)
    - "Registro relacionado não encontrado" (P2003)
    - "Erro interno do servidor" (fallback)
  • "Sessão encerrada com sucesso" no logout

Princípios:
  • Consistência — toda a comunicação com o cliente está no mesmo
    idioma (português)
  • Intenção clara — mensagens descritivas em vez de códigos genéricos

Arquivos:
  src/equipments/equipments.service.ts  (MODIFICADO)
  src/admin/admin.service.ts            (MODIFICADO)
  src/common/filters/prisma-exception.filter.ts (MODIFICADO)
  src/auth/auth.controller.ts           (MODIFICADO)

5. LOGGER NO LUGAR DE console.error
----------------------------------------------------------------------
Antes:
  PrismaExceptionFilter usava console.error() diretamente.

Depois:
  Usa Logger do NestJS (PrismaExceptionFilter.name), que:
  • Segue o formato padronizado de logs do NestJS
  • Pode ser desabilitado/redirecionado via configuração
  • Inclui contexto automático no log

Princípios:
  • Infrastructure segregation — abstração do mecanismo de log
  • Dependência estável — depende do Logger do NestJS em vez de
    console global

Arquivos:
  src/common/filters/prisma-exception.filter.ts (MODIFICADO)

6. EquipmentDto: model OBRIGATÓRIO CORRIGIDO
----------------------------------------------------------------------
Antes:
  O campo model estava anotado com @IsNotEmpty() (obrigatório na
  validação) mas marcado como model?: string (opcional no TypeScript).
  Isso criava uma contradição entre a tipagem e a validação.

Depois:
  model: string (sem o ?). A assinatura agora corresponde à validação.

Princípios:
  • Consistência — a type assertion reflete a validação real
  • Menos surpresas — não há contradição entre tipo e runtime

Arquivos:
  src/equipments/dtos/equipment.dto.ts (MODIFICADO)

7. HELPER DE COOKIE (DRY)
----------------------------------------------------------------------
Antes:
  A lógica de criar o cookie `refresh_token` estava duplicada em 3
  lugares no AuthController (signIn, logout, refresh), cada um
  recalculando isSecure e montando o mesmo objeto de options.

Depois:
  Criadas duas funções em src/common/utils/cookie.ts:
    refreshTokenCookieOptions()  → para setar o cookie
    clearRefreshTokenCookieOptions() → para limpar o cookie
  Ambos os métodos no controller agora chamam essas funções.

Princípios:
  • DRY — as opções do cookie existem em um único lugar
  • Nome intencional — o nome da função revela a intenção
  • Manutenibilidade — para alterar as opções do cookie, muda-se
    um único arquivo

Arquivos:
  src/common/utils/cookie.ts         (CRIADO)
  src/auth/auth.controller.ts        (MODIFICADO)

8. TIPO SanitizedRow ELIMINA `as any`
----------------------------------------------------------------------
Antes:
  sanitizeRow() retornava Record<string, any>, e importConfirm()
  usava sanitized as any para chamar prisma.equipment.create().
  Isso desligava completamente a verificação de tipos.

Depois:
  • Criado o tipo SanitizedRow com os campos esperados:
      name?, model?, assetTag?, serialNumber?, location?,
      ipAddress?, description?, status? (Estado)
  • sanitizeRow() retorna SanitizedRow
  • importConfirm() usa as Prisma.EquipmentCreateInput para o
    cast, que é seguro porque SanitizedRow é um subtipo

Princípios:
  • Type Safety — o compilador pode verificar se os campos estão
    corretos
  • Nenhum any — zero escapes de tipo
  • Acoplamento mínimo — SanitizedRow conhece apenas os campos
    relevantes, não o schema inteiro do Prisma

Arquivos:
  src/equipments/equipments.service.ts (MODIFICADO)

9. bootstrap().catch() COM LOG
----------------------------------------------------------------------
Antes:
  bootstrap().catch(() => process.exit(1)) — engolia o erro.

Depois:
  bootstrap().catch((err) => {
    console.error('Falha ao iniciar servidor', err);
    process.exit(1);
  });

Princípios:
  • Falha ruidosa (Fail Fast) — erros de inicialização são
    registrados antes de encerrar
  • Diagnóstico — a causa raiz fica visível nos logs

Arquivos:
  src/main.ts (MODIFICADO)

10. TIPOS DE RETORNO EXPLÍCITOS
----------------------------------------------------------------------
Antes:
  Vários métodos importantes (findAll, exportCsv, exportXlsx,
  importPreview, importConfirm) não declaravam tipo de retorno,
  deixando o TypeScript inferir.

Depois:
  Adicionados tipos de retorno explícitos onde fazia sentido:
  • exportCsv(): Promise<{ buffer: Buffer; filename: string }>
  • exportXlsx(): Promise<{ buffer: Buffer; filename: string }>
  • importPreview(): Promise<ImportPreviewResult>
  • importConfirm(): Promise<ImportResult>
  • getFirstAdminId(): Promise<string | null>
  • getPasswordHash(): Promise<string>
  hasChanges(): boolean e validadores retornam boolean

Princípios:
  • Contrato explícito — quem chama o método sabe exatamente o que
    esperar sem precisar ler a implementação
  • Documentação viva — o tipo de retorno é documentação executável

Arquivos:
  src/equipments/equipments.service.ts (MODIFICADO)

11. validateRow PURA (SEM MUTAÇÃO)
----------------------------------------------------------------------
Antes:
  validateRow(record, row, errors) recebia um array errors por
  referência e mutava ele com errors.push(). Isso é um efeito
  colateral invisível para quem chama.

Depois:
  validateRow(record): string[] retorna um array de erros. Quem
  chama decide o que fazer com ele (push, early return, etc.).

Princípios:
  • Imutabilidade — a função não modifica argumentos externos
  • Efeito zero — nenhum side effect
  • Previsibilidade — a assinatura comunica claramente: entra
    record, sai string[]

Arquivos:
  src/equipments/equipments.service.ts (MODIFICADO)

12. TIPO DISCRIMINADO RowAction
----------------------------------------------------------------------
Antes:
  resolveRowAction retornava um tipo genérico
  { action: string; record?: ...; message?: ... } — qualquer
  combinação era possível, action aceitava qualquer string.

Depois:
  Criado o tipo discriminado (union):
    type RowAction =
      | { action: 'create' }
      | { action: 'update'; record: { id: string } }
      | { action: 'skip'; record: { id: string } }
      | { action: 'error'; message: string }

  O switch/case no importPreview agora usa Type Guard:
    if (action.action === 'update') → TypeScript sabe que
    action.record existe.

Princípios:
  • Type Safety — impossível acessar record quando action é 'error'
  • Discriminated Union — padrão idiomático do TypeScript para
    resultados com forma variável

Arquivos:
  src/common/utils/import-types.ts           (CRIADO)
  src/equipments/equipments.service.ts       (MODIFICADO)
